# Безопасность

## Уже реализовано

- Секреты не встраиваются в клиент и не входят в модель локальных настроек.
- Любой путь из будущего манифеста проходит проверку и разрешается строго внутри папки установки.
- Поддерживаются проверки размера и SHA-256 каждого файла.
- Повреждённый JSON настроек не приводит к падению приложения.
- Настройки записываются через временный файл и атомарную замену.
- Основные проверки покрыты автоматическими тестами.
- Манифест лаунчера подписывается ECDSA P-256; клиент содержит только публичный ключ.
- Загрузка разрешена только по HTTPS с того же origin, что и настроенная база R2.
- Оборванный пакет сохраняется как `.part`, а превышение подписанного размера отклоняется.
- ZIP распаковывается в отдельный staging-каталог с защитой от path traversal, дубликатов, символических ссылок и zip bomb.
- Новая версия активируется отдельной записью состояния; предыдущая сохраняется до сигнала успешного запуска.
- Авторизация открывается только в системном браузере; лаунчер не принимает пароль и коды 2FA.
- Нативный OAuth-клиент использует случайные `state`, `nonce`, PKCE S256 и проверяет параметр издателя `iss`.
- Возврат разрешён только на точный loopback-путь `127.0.0.1`; порт выбирается случайно.
- В лаунчер не встраивается OAuth client secret.
- Токены шифруются Windows DPAPI для текущего пользователя и не попадают в обычный файл настроек.
- При выходе refresh token отзывается через стандартный OAuth 2.0 revocation endpoint, затем локальная DPAPI-сессия удаляется.

## Ещё не реализовано

- подключение постоянного R2 custom domain;
- создание и резервное копирование production-ключа подписи вне репозитория;
- UI прогресса, паузы и понятных ошибок;
- интеграционные тесты сбоя питания на реальной установленной сборке;
- подпись исполняемых файлов сертификатом code signing;
- экран управления и массового отзыва OAuth-сессий всех приложений в TRYNEX ID.

## Обязательная схема будущего обновления

1. Получить подписанный манифест по HTTPS с настроенного R2 origin.
2. Проверить подпись встроенным публичным ключом.
3. Провалидировать все относительные пути и размеры до скачивания.
4. Скачать файлы в отдельный staging-каталог.
5. Проверить SHA-256 каждого скачанного файла.
6. Bootstrapper переключает активную версию записью атомарного локального состояния.
7. При любой ошибке восстановить предыдущую рабочую версию.
8. Удалить резервную копию только после успешного запуска и подтверждения здоровья.

Никогда нельзя удалять текущую установку до полной проверки новой версии.

## Сообщение об уязвимости

До появления отдельного security-адреса уязвимость не следует публиковать вместе с рабочим эксплойтом. Сначала создаётся приватный канал связи и регламент ответов.
